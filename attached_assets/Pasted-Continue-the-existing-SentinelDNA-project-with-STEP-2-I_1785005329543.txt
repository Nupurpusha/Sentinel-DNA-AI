==================================================
STEP 2 — ML-BASED BEHAVIORAL ANOMALY DETECTION
==================================================

The goal of Step 2 is to transform SentinelDNA from a synthetic telemetry viewer into an actual behavioral anomaly detection system.

The system must LEARN what is normal for each identity from behavioral data and detect deviations WITHOUT using the ground-truth label to calculate anomaly scores.

CRITICAL DATA-LEAKAGE RULE:

The existing `label` field (normal, brute_force, impossible_travel, credential_stuffing, lateral_movement, device_spoofing, low_slow_exfiltration, insider_drift, etc.) is GROUND TRUTH ONLY.

NEVER use `label` as:
- an ML feature
- an input to anomaly scoring
- an input to risk scoring
- a rule for deciding whether an event is anomalous

The model must infer abnormal behavior independently.

The label may ONLY be used AFTER scoring for evaluation of model performance.

1. FEATURE ENGINEERING
==================================================

Build behavioral features from the existing event data.

Include useful features such as:

- hour of day

- authentication success/failure

- known vs unknown device
- resource familiarity
- location familiarity
- IP/subnet familiarity

==================================================
2. BEHAVIORAL BASELINE LEARNING
==================================================

Learn behavioral baselines from historical events.

Where possible, calculate identity-specific baselines for:

- normal login/access hours
- normal locations
- known devices
- common resources
- preferred authentication methods
- normal session duration
- usual IP/subnet behavior
- normal access frequency

The model should detect deviation from an identity's own historical behavior, not simply compare every identity against one global average.

==================================================
3. UNSUPERVISED ML ANOMALY DETECTION
==================================================

Implement an unsupervised anomaly detection model.

Isolation Forest is preferred unless inspection of the existing architecture shows that another lightweight unsupervised method is more appropriate.

Train the detector WITHOUT using the `label` column.

For every event generate at minimum:

- anomaly_score
- risk_score (0–100)
- predicted_anomaly (true/false)
- risk_level (Low / Medium / High / Critical)

Persist or cache the trained model appropriately so the application does NOT retrain unnecessarily on every API request.

Make the implementation reproducible by using a fixed random seed where appropriate.

- Unusual authentication method

- Abnormal access frequency

Do NOT derive explanations from the ground-truth label.
